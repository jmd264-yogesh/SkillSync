# Capacity Simulator — How It Works

**Route:** `/admin/resourcing/simulator`  
**Access:** ADMIN only  
**AI model:** Gemini 1.5 Pro, temperature 0.15  
**Key files:** `simulator/page.tsx`, `simulator/simulator-client.tsx`, `proposition-simulator.ts`, `historical-allocations.ts`

---

## Overview

The Capacity Simulator lets resource managers model the team needed for an upcoming engagement. Given a proposition type, project type, phase, and criticality it returns two side-by-side views:

- **Historical Baseline** — exact deterministic lookup from 34 past allocation patterns. No AI, no variance.
- **AI Recommendation** — Gemini reads the historical table as its anchor and then applies adjustments for source systems, tech stack, and any freetext context.

After running, you can search the live talent pool for candidates matching the recommended roles.

---

## How a simulation runs

1. Fill the form (Proposition, Project Type, Phase, Criticality, Start Date, Weeks).
2. Optionally expand **Source Systems**, **Tech Stack**, or **Additional Context**.
3. Click **Run Simulation** — `simulateProposition()` server action fires. It does:
   - Deterministic baseline lookup from `HISTORICAL_ALLOCATIONS`
   - Gemini call with the baseline as anchor + all optional inputs
4. Results appear side-by-side: Historical Baseline (left) · AI Recommendation (right).
5. Optionally: click **Find Resources**, toggle "Based on" (AI or Baseline), get top 5 candidates per role.

## Form inputs

| Field | Required | Effect |
|-------|----------|--------|
| Proposition | Yes | Service line (Data Advisory, Core Reporting, etc.). Filters Project Type. Context for AI only. |
| Project Type | Yes | Solution domain (Customer, Sales, Finance, Operations, People, Full Stack, …). Primary baseline key + AI anchor. |
| Phase | Yes | `Design & Discovery` = lighter footprint. `Build` = full delivery team including SSE and SW. Second baseline key. |
| Criticality | Yes | `Stable` = lean. `Medium` = standard. `High` = expanded delivery + tech. Third baseline key. |
| Start Date | Yes | Availability window start for match engine. |
| Weeks | Yes | Duration context for AI. Availability window end = start + weeks. |

## Optional inputs

### Source Systems
Multi-select from 15 predefined platforms (Salesforce, Snowflake, SAP, etc.).  
Affects **Chennai engineering headcount only** — see [Source System Scaling](#source-system-scaling) below.  
UK consulting roles are never affected.

### Tech Stack
Multi-select from all skills in the platform DB, grouped by category (Tools, Frameworks, Skills, Concepts, Certifications).

Two effects:
1. Sent to AI as context — Chennai technical roles implement these tools.
2. Passed to the match engine as `requiredSkills` at level 3 (Intermediate) — candidates with these skills score higher in Find Resources.

### Additional Context
Freetext textarea. Wrapped in `<context>…</context>` and sent to Gemini as part of the user message.  
Use for anything the structured fields can't capture: data volumes, client specifics, delivery constraints.  
Source counts mentioned here (e.g. "25 source systems") are picked up by the AI and trigger the scaling table.

> **Note:** A freetext source count takes precedence over the Source Systems checkbox count in practice, because the AI reads the full message.

## Historical Baseline

Stored in `src/lib/historical-allocations.ts` as `HISTORICAL_ALLOCATIONS` — 34 rows.  
Fully deterministic. Same inputs always return the same output, no AI call involved.

**Lookup key** — all three must match exactly (case-insensitive):

| Dimension | Values |
|-----------|--------|
| Solution | Customer · Sales · Finance · Operations · People · Full Stack · Churn Prediction · Lead Scoring · Migration |
| Phase | Design & Discovery · Build |
| Criticality | Stable · Medium · High |

If no row matches, the baseline panel shows "no match found" and the AI uses the nearest reference pattern.

**Roles with historical data** (only 7 of the 19 proposition roles):

| Role | Location |
|------|----------|
| Technical Solutions Architect | Chennai |
| Consultant | UK |
| Associate Consultant | Chennai |
| Solutions Consultant | Chennai |
| Solutions Enabler | Chennai |
| Senior Software Engineer | Chennai |
| Software Engineer | Chennai |

### Example: Customer · Build · Medium

| Role | Allocation |
|------|-----------|
| Technical Solutions Architect | 25% |
| Consultant | 1× 100% |
| Associate Consultant | 1× 100% |
| Solutions Consultant | 1× 100% |
| Solutions Enabler | 1× 100% |
| Senior Software Engineer | 1× 100% |
| Software Engineer | 2× 100% |

## AI Recommendation

Generated by **Gemini 1.5 Pro** at **temperature 0.15** (near-deterministic).  
The system prompt embeds the full historical reference table as the AI's primary anchor.

### What the AI receives

| Input | Content |
|-------|---------|
| System prompt | Full historical reference table, UK/Chennai philosophy, source system scaling table, list of all 19 roles |
| Baseline anchor | If a baseline match was found, its exact headcounts: *"Use these as your primary anchor"* |
| Source note | Selected source systems + reminder that each system adds Chennai engineering overhead |
| Tech stack note | Selected skills + note that Chennai technical roles implement them |
| Context | Freetext wrapped in `<context>` tags |

### What the AI returns

```json
{
  "allocations": [
    { "role": "Software Engineer", "allocation": 3 },
    { "role": "Senior Software Engineer", "allocation": 1.5 }
  ],
  "narrative": "Finance/Build/Medium baseline used. 5 sources detected — +1 SW +0.5 SSE added.",
  "totalHeadcount": 9.5
}
```

Values are **headcount numbers**, not percentages. `1.0` = one person full-time, `0.5` = half-time, `2.0` = two people.  
The UI converts these to the `N× 100%` / `X%` display format.

### Key constraint

The AI is explicitly told: *"Do NOT drift from the historical patterns without explaining why in the narrative."* If it deviates, the rationale must state exactly what changed and why.

## UK vs Chennai split

The 19 proposition roles are divided into two location groups with different headcount drivers.

### UK roles — advisory and client-facing

**Headcount driver: client relationship complexity** (stakeholder seniority, governance weight).  
Does **not** increase with source systems, tech stack, or data volume.

`Partner` · `Associate Partner` · `Principal` · `Manager` · `Senior Consultant` · `Consultant`

### Chennai roles — delivery and technical

**Headcount driver: technical complexity** (source systems, data volume, build scope).  
Scales with every dimension of engineering work.

`Technical Solutions Architect` · `Senior Solutions Consultant` · `Solutions Consultant` · `Solutions Enabler` · `Senior Software Engineer` · `Software Engineer` · `Senior Associate Consultant` · `Associate Consultant` · `Partner Technology` · `Associate Partner Technology` · `Principal Technology Architect` · `Intern` · `Intern Technology`

## Source system scaling

> **Critical:** The historical baseline has **zero source system overhead built in**. Every source system — even just 1 — requires engineering effort (connector build, data modelling, testing, maintenance). The AI always adds the following on top of the baseline for any source count.

Additions are **additive** on top of the baseline. Roles added: SW (Software Engineer), SSE (Senior Software Engineer), TA (Technical Solutions Architect), SE (Solutions Enabler).

| Source count | SW | SSE | TA | SE |
|---|---|---|---|---|
| 1–2 | +0.5 | — | — | — |
| 3–5 | +1 | +0.5 | — | — |
| 6–10 | +2 | +1 | +0.25 | — |
| 11–15 | +3 | +1.5 | +0.5 | +0.25 |
| 16–20 | +4 | +2 | +0.75 | +0.5 |
| 21–30 | +5 | +2.5 | +1 | +1 |
| 30+ | +6 | +3 | +1.5 | +1.5 |

**Example:** Finance · Build · Medium baseline + 5 sources:  
Baseline = 1C + 1AC + 1SC + 1SE + 1SSE + 2SW → add +1SW +0.5SSE → final = 1C + 1AC + 1SC + 1SE + 1.5SSE + 3SW

## Find Resources

After a simulation runs, the Find Resources card appears. It calls `computeMatchRanking()` — the same engine used by the Match Engine page and Excel export — for each active role and returns the top 5 candidates.

### Source toggle

| Mode | Input to match engine | When to use |
|------|----------------------|-------------|
| **AI Recommendation** | Gemini-generated headcounts including all adjustments | When you want candidates after source/tech/context changes |
| **Historical Baseline** | Exact historical lookup values (only active if a match exists) | When you want candidates against the known-good historical pattern |

### Scoring dimensions

`computeMatchRanking()` scores each employee across 7 weighted dimensions:

| Dimension | Weight | What it measures |
|-----------|--------|-----------------|
| Skill coverage | 32% | Required skills held × proficiency depth |
| Competency | 22% | Avg score across 5 consulting behaviours |
| Availability | 18% | Free capacity in the project window |
| Billability | 10% | Low billability = high cost-recovery opportunity |
| Experience | 8% | Validated skill-level depth |
| Evidence | 6% | Certs, project docs, role history |
| COE alignment | 4% | Employee COE matches project solution domain |

### Signal badges

| Signal | Meaning |
|--------|---------|
| `REDEPLOY` (green) | Strong internal fit |
| `PARTIAL_HIRE` (amber) | Partial fit — skill gap, upskilling likely needed |
| `HIRE` (red) | No internal match — recommend external hire |

### Score breakdown (expandable rows)

Click any candidate row to expand a detail panel showing:
- **Score bars** for each of the 5 stored dimensions (colour coded: green ≥ 75, amber 50–74, red < 50)
- **Skill gaps** — skills required by tech stack that the candidate doesn't hold
- **Skill coverage** — confirmation when all required skills are matched

## Allocation display format

| Raw value | Displayed as | Meaning |
|-----------|-------------|---------|
| `2.0` | **2× 100%** | Two people, each full-time |
| `1.0` | **1× 100%** | One person full-time |
| `0.5` | **50%** | One person at half capacity |
| `0.25` | **25%** | One day per week |
| `0.12` | **12%** | ~One day per fortnight |

Rule: if value ≥ 1 → `{value}× 100%`; else → `{Math.round(value * 100)}%`.  
The word "FTE" does not appear anywhere in the UI.
